## The six axes

### 1. Team/development architecture (solo vs team, number of agents, human vs agent role, sessions, subagents)

**Default shape: one human, one interactive session at a time, subagents for scoped AFK work.** The repo is literally his personal toolkit ("Straight from my .agents directory"), and the main flow assumes a single driving developer. Parallelism is achieved by *sessions*, not by a multi-agent framework: after `/to-tickets`, "any ticket whose blockers are done can be grabbed: kick off **`/implement`** per ticket, **`/clear`ing context between each one**" ([ask-matt](research/1-matt-pocock/skills-repo/skills/engineering/ask-matt/SKILL.md)). The to-tickets docs are blunt that dispatch is manual: "The skill stops at the artifact, and there is no auto-dispatch mode. Dispatch is manual: look at the board, count the tickets with no open blockers, and open that many agent sessions. One ticket per fresh context, cleared between them." ([docs/engineering/to-tickets.md](research/1-matt-pocock/skills-repo/docs/engineering/to-tickets.md))

**Parallel `/implement` in one checkout is explicitly unsupported.** "No. One invocation, one ticket. Batch dispatch across a ticket queue and subagent fan-out are both requested repeatedly, and neither exists. Running several `/implement` sessions side by side in one checkout is worse than unsupported... The sessions share one working directory, one index, and one HEAD. Git worktrees are the community workaround... If you want parallelism today, you are assembling it yourself." ([docs/engineering/implement.md](research/1-matt-pocock/skills-repo/docs/engineering/implement.md))

**Where multi-agent lives: the beta `implement-spec` and the separate Sandcastle project.** The in-progress `implement-spec` skill (added in an unreleased changeset after v1.2.3) is the first orchestrator in the repo: "The tickets are not a list of steps. They are a **task graph** with blocking relationships... **Implementer subagents** should be run in the background where possible for **maximum concurrency**." Each "implementer subagent should work in its own worktree, on its own branch", a "**merger subagent**" folds work back, and the flow ends with `/code-review` and a PR marked ready ([in-progress/implement-spec/SKILL.md](research/1-matt-pocock/skills-repo/skills/in-progress/implement-spec/SKILL.md); [.changeset/add-implement-spec-skill.md](research/1-matt-pocock/skills-repo/.changeset/add-implement-spec-skill.md)). Outside the repo, [Sandcastle](https://github.com/mattpocock/sandcastle) (7.5k stars, 1,193 commits) orchestrates agents in Docker/Podman/Vercel sandboxes with worktree branch strategies and templates like "simple-loop" ("picks issues one by one and closes them") and "sequential-reviewer". Secondhand workshop summaries describe his AFK setup as "Sonnet implements, Opus reviews in parallel, then a third agent merges branches" ([talksintel](https://talksintel.ai/ai-ml/conferences/aie-eu-2026/full-walkthrough-workflow-for-ai-coding-matt-pocock/)).

**Subagents inside the skills** (all in the shipped set):
- `/grilling`: "When a frontier question needs a fact from the environment... dispatch a sub-agent to find it; don't ask the user for anything you could look up yourself." ([grilling SKILL.md](research/1-matt-pocock/skills-repo/skills/productivity/grilling/SKILL.md))
- `/code-review`: "Both axes run as **parallel sub-agents** so they don't pollute each other's context" ([code-review SKILL.md](research/1-matt-pocock/skills-repo/skills/engineering/code-review/SKILL.md)).
- `/research`: "Spin up a **background agent** to do the research, so you keep working while it reads." ([research SKILL.md](research/1-matt-pocock/skills-repo/skills/engineering/research/SKILL.md))
- `/improve-codebase-architecture`: "spawn a sub-agent to walk the codebase" ([SKILL.md](research/1-matt-pocock/skills-repo/skills/engineering/improve-codebase-architecture/SKILL.md)).
- `/codebase-design` DESIGN-IT-TWICE: "Spawn 3+ sub-agents in parallel. Each must produce a **radically different** interface" ([DESIGN-IT-TWICE.md](research/1-matt-pocock/skills-repo/skills/engineering/codebase-design/DESIGN-IT-TWICE.md)).
- `/wayfinder`: "For each `research` ticket you just created, spin up a subagent that calls the Skill tool with 'research' to resolve it in parallel" ([wayfinder SKILL.md](research/1-matt-pocock/skills-repo/skills/engineering/wayfinder/SKILL.md)).

**Human role vs agent role.** The split is stated in several places: facts are the agent's, decisions are the human's (grilling); the human "is the index" of which skills exist ("Cognitive load is the cost on the human... The human is the index. Not a cost to minimise: it is the price of human agency" — [writing-for-agents SKILL.md](research/1-matt-pocock/skills-repo/skills/productivity/writing-for-agents/SKILL.md)); the human owns interfaces while "AI owns the implementation" with tests as the enforcement mechanism ([How To Make Codebases AI Agents Love](https://www.aihero.dev/how-to-make-codebases-ai-agents-love)). Secondhand workshop notes: "He acknowledges alignment and QA cannot be delegated; AI increases code review burden rather than reducing it." ([biggo workshop summary](https://finance.biggo.com/news/e7209c094224b09c))

**Sessions.** One phase-boundary decision tree governs session handling ([PHASE-BOUNDARIES.md](research/1-matt-pocock/skills-repo/skills/engineering/ask-matt/PHASE-BOUNDARIES.md)): "**1. Can you continue in this session?**... Grilling → implementation is the standard yes... **2. Is the context irrelevant to what comes next?** If so, **`/clear`**... **3. Do you need to hand off?** `/handoff` is narrow... **4. Can the task be done AFK?** Then send it to a **subagent**... **5. Otherwise, `/compact`.**" Also: "Every move except **Continue** turns a **primary source** into a **secondary source**". Note the tension with older secondhand reports that he "prefers starting fresh rather than compacting session history" ([biggo](https://finance.biggo.com/news/e7209c094224b09c)); the shipped router (v1.2) explicitly makes `/compact` "the **default, not the first reach**."

**Team use.** Wayfinder was made "Collaborative by default. The map moves off a local Markdown file onto the repo's issue tracker: a single `wayfinder:map` issue whose tickets are its child issues — one shared URL the team can watch." ([CHANGELOG 1.1.0](research/1-matt-pocock/skills-repo/CHANGELOG.md)) `/triage` is for maintainers receiving outside issues/PRs ("The main use is open-source repos taking issues from external contributors" — [docs/engineering/triage.md](research/1-matt-pocock/skills-repo/docs/engineering/triage.md)). `/to-questionnaire` exists for "a decision blocked on knowledge that lives in one other person's head". The "9 things" article also recommends running 2–3 *parallel grilling sessions* like Slack threads ([aihero.dev](https://www.aihero.dev/things-people-get-wrong-with-grill-me-and-grill-with-docs)). Secondhand assessment: the skills "encode 'how Matt Pocock engineers — a TypeScript-heavy, library-and-teaching-oriented practice'" ([alexrusin, 2026-08-07](https://blog.alexrusin.com/agentic-coding-pipeline-matt-pocock-skills/)).

### 2. Brownfield handling (existing codebase; building understanding; CONTEXT.md/domain model)

**There is no dedicated "onboard to a codebase" skill; brownfield understanding is built through the same domain-modeling discipline, applied deliberately.** The documented route: "`/grill-with-docs help me scaffold my existing repo with a CONTEXT.md` is the documented route; expect a long interrogation: one user reported 50+ questions before the file was in shape. Incidental use builds the glossary far too slowly on a brownfield repo." ([docs/engineering/domain-modeling.md](research/1-matt-pocock/skills-repo/docs/engineering/domain-modeling.md)) And: "This is the right skill for a codebase with no ADRs, no domain language and no design principles: invoke it and say 'help me document my repo'. The community pattern pairs it with improve-codebase-architecture for building or repairing a `CONTEXT.md`. Expect to steer it: it will read code and ask you about what it finds, and you are the one who says which of the words already in the codebase are the right ones." ([docs/engineering/grill-with-docs.md](research/1-matt-pocock/skills-repo/docs/engineering/grill-with-docs.md))

**What `CONTEXT.md` is (and is not).** "`CONTEXT.md` should be totally devoid of implementation details. Do not treat `CONTEXT.md` as a spec, a scratch pad, or a repository for implementation decisions. It is a glossary and nothing else." ([domain-modeling SKILL.md](research/1-matt-pocock/skills-repo/skills/engineering/domain-modeling/SKILL.md)) Format: `**Term**: one or two sentence definition` plus `_Avoid_: synonyms`; "Be opinionated", "Only include terms specific to this project's context" ([CONTEXT-FORMAT.md](research/1-matt-pocock/skills-repo/skills/engineering/domain-modeling/CONTEXT-FORMAT.md)). Multi-context repos use a root `CONTEXT-MAP.md` pointing to per-context `CONTEXT.md` files (DDD bounded contexts). The repo's own [CONTEXT.md](research/1-matt-pocock/skills-repo/CONTEXT.md) is a worked example (terms: Issue tracker, Issue, Decision ticket, Triage role; plus "Flagged ambiguities"). His `course-video-manager` CONTEXT.md has ~40 terms in six categories with a "Flagged Ambiguities" section ([course-video-manager CONTEXT.md](https://github.com/mattpocock/course-video-manager/blob/076a5a7a182db0fe1e62971dd7a68bcadf010f1c/CONTEXT.md)).

**ADRs** live in `docs/adr/NNNN-slug.md`; the template is "1-3 sentences: what's the context, what did we decide, and why." Offer one only when all three hold: "**Hard to reverse**... **Surprising without context**... **The result of a real trade-off**" ([ADR-FORMAT.md](research/1-matt-pocock/skills-repo/skills/engineering/domain-modeling/ADR-FORMAT.md)). Why: "This alignment between you and the AI on non-obvious decisions prevents the AI from suggesting the same bad idea repeatedly." ([Skills Changelog: Ubiquitous Language → /grill-with-docs, 2026-04-30](https://www.aihero.dev/skills-changelog-ubiquitous-language-grill-with-docs))

**Consumer rules every engineering skill follows** ([setup template domain.md](research/1-matt-pocock/skills-repo/skills/engineering/setup-matt-pocock-skills/domain.md)): "Before exploring, read these: `CONTEXT.md`... `docs/adr/`... If any of these files don't exist, **proceed silently**." "If the concept you need isn't in the glossary yet, that's a signal: either you're inventing language the project doesn't use (reconsider) or there's a real gap." "If your output contradicts an existing ADR, surface it explicitly rather than silently overriding".

**Cross-referencing code against what you say** is the move that makes domain-modeling brownfield-aware: "When the user states how something works, check whether the code agrees. If you find a contradiction, surface it: 'Your code cancels entire Orders, but you just said partial cancellation is possible. Which is right?'" ([domain-modeling SKILL.md](research/1-matt-pocock/skills-repo/skills/engineering/domain-modeling/SKILL.md)) Limit: "It cross-references **code** and the committed `CONTEXT.md`/ADRs, and nothing else. It does not search your issue tracker" ([docs/engineering/domain-modeling.md](research/1-matt-pocock/skills-repo/docs/engineering/domain-modeling.md)).

**Architecture survey for brownfield.** `/improve-codebase-architecture` is listed for "Brownfield audit: Run it on a large, unstructured or vibe-coded repo to find out what shape it is actually in" and "Legacy test work: Use it to find the missing seams first, before writing tests against untestable code" — but with the honest counterweight: "users with genuinely out-of-control projects report it 'helped a little but still doesn't seem to cut it,' and one developer with an eight-year legacy codebase reported the model going in circles... If the codebase has no shared vocabulary at all, grill-with-docs to establish one first tends to make this skill's output much better." ([docs/engineering/improve-codebase-architecture.md](research/1-matt-pocock/skills-repo/docs/engineering/improve-codebase-architecture.md)) The README itself: "It is a survey, not a rescue: on a genuinely old codebase it will find real candidates, but it won't untangle the mud for you."

**Wayfinder on legacy code.** "Greenfield is not a requirement. Wayfinder is used routinely on legacy and half-built codebases, and it is arguably sharper there, because a lot of the fog is 'what is already true here' rather than 'what should we do'." ([docs/engineering/wayfinder.md](research/1-matt-pocock/skills-repo/docs/engineering/wayfinder.md))

**Setup reads what's already there.** `/setup-matt-pocock-skills` explores `git remote`, existing `CLAUDE.md`/`AGENTS.md`, `CONTEXT.md`, `docs/adr/`, `.scratch/`, monorepo signals before proposing anything ([setup SKILL.md](research/1-matt-pocock/skills-repo/skills/engineering/setup-matt-pocock-skills/SKILL.md)); "A repo already halfway through a project is a fine place to run it" ([docs page](research/1-matt-pocock/skills-repo/docs/engineering/setup-matt-pocock-skills.md)).

**Honest limits.** The value of the glossary for the *agent* is debated even in Matt's own docs: "not everyone agrees this buys you agent performance: the sharpest public pushback is that a term and its plain-English expansion get the same result from the model, and that the vocabulary really compresses communication between the humans who share it." ([docs/engineering/grill-with-docs.md](research/1-matt-pocock/skills-repo/docs/engineering/grill-with-docs.md)) And a warning relevant to a beginner: "an unreviewed, agent-authored glossary is worse than none: it becomes confident-sounding lore that later sessions treat as truth" and "A domain language you do not understand yourself becomes meaningless drivel once written down." ([docs/engineering/domain-modeling.md](research/1-matt-pocock/skills-repo/docs/engineering/domain-modeling.md))

### 3. Adding new code & handling changes/contributions (specs, tickets, tracer bullets, PR/review, tests, commits)

**Specs.** `/to-spec`: "This skill takes the current conversation context and codebase understanding and produces a spec. Do NOT interview the user; just synthesize what you already know." Before writing: "Sketch out the seams at which you're going to test the feature. Existing seams should be preferred to new ones. Use the highest seam possible... The fewer seams across the codebase, the better - the ideal number is one. Check with the user that these seams match their expectations." Template sections: Problem Statement, Solution, User Stories ("A LONG, numbered list"), Implementation Decisions ("Do NOT include specific file paths or code snippets. They may end up being outdated very quickly."), Testing Decisions, Out of Scope, Further Notes. Published to the tracker with the `ready-for-agent` label ([to-spec SKILL.md](research/1-matt-pocock/skills-repo/skills/engineering/to-spec/SKILL.md)). Matt's docs call the spec "a decision record": "Anything the spec asserts that you never actually said is a defect" and "Treat it as throwaway once the work ships. The artifacts meant to outlive it are your `CONTEXT.md` and your ADRs" ([docs/engineering/to-spec.md](research/1-matt-pocock/skills-repo/docs/engineering/to-spec.md)).

**Tickets = tracer bullets with blocking edges.** `/to-tickets` rules: "Each slice cuts a narrow but COMPLETE path through every layer (schema, API, UI, tests): vertical, NOT a horizontal slice of one layer; A completed slice is demoable or verifiable on its own; Each slice is sized to fit in a single fresh context window; Any prefactoring should be done first." Also: "Look for opportunities to prefactor the code to make the implementation easier. 'Make the change easy, then make the easy change.'" Wide refactors are the exception, sequenced as **expand–contract**. The breakdown is quizzed with the user ("Does the granularity feel right?... Are the blocking edges correct...") before publishing. Local files go to `.scratch/<feature-slug>/issues/<NN>-<slug>.md`, numbered blockers-first; on a real tracker, one issue per ticket with native blocking/sub-issue links and the `ready-for-agent` label ([to-tickets SKILL.md](research/1-matt-pocock/skills-repo/skills/engineering/to-tickets/SKILL.md)). The philosophical source: "When building features, build a tiny, end-to-end slice of the feature first, seek feedback, then expand out from there." ([Tracer Bullets: Keeping AI Slop Under Control, 2026-01-22](https://www.aihero.dev/tracer-bullets))

**Implementation.** `/implement` is deliberately tiny: "Implement the work described by the user in the spec or tickets. Use /tdd where possible, at pre-agreed seams. Run typechecking regularly, single test files regularly, and the full test suite once at the end. Once done, use /code-review to review the work. Commit your work to the current branch." ([implement SKILL.md](research/1-matt-pocock/skills-repo/skills/engineering/implement/SKILL.md)) It "never reopens the plan" and "commits to the branch you are on. It does not create one, and it does not ask." ([docs/engineering/implement.md](research/1-matt-pocock/skills-repo/docs/engineering/implement.md))

**Tests.** `/tdd`: "TDD is the red → green loop." "**Test only at pre-agreed seams.** Before writing any test, write down the seams under test and confirm them with the user." Anti-patterns: implementation-coupled, tautological, horizontal slicing. "**Refactoring is not part of the loop.** It belongs to the review stage." Mock only at system boundaries ([tdd SKILL.md](research/1-matt-pocock/skills-repo/skills/engineering/tdd/SKILL.md), [mocking.md](research/1-matt-pocock/skills-repo/skills/engineering/tdd/mocking.md)). The refactor step "was dropped in June 2026 because agents essentially never performed it, and because review and implementation work better as separate sessions" ([docs/engineering/tdd.md](research/1-matt-pocock/skills-repo/docs/engineering/tdd.md)). Matt: "Doing really good TDD has been the most consistent way to improve agent outputs." ([5 Agent Skills](https://www.aihero.dev/5-agent-skills-i-use-every-day))

**Review.** `/code-review` diffs `git diff <fixed-point>...HEAD` on two axes ("**Standards**: does the code conform to this repo's documented coding standards? **Spec**: does the code faithfully implement the originating issue / spec?"), with a fixed Fowler smell baseline (12 smells) that "is always a judgement call" and where "the repo overrides". It never merges the two reports: "Don't pick a single winner across axes." ([code-review SKILL.md](research/1-matt-pocock/skills-repo/skills/engineering/code-review/SKILL.md)) Preference for fresh-context review: "Same context reviewing itself isn't review, it's confirmation bias with a slash command." ([docs/engineering/code-review.md](research/1-matt-pocock/skills-repo/docs/engineering/code-review.md), quoting a reader; Matt's workshop practice per secondhand notes is "always in fresh context").

**Commits and PRs.** The shipped flow commits to the current branch; "Can it open a pull request instead of committing? Not built in... People override it in the invocation ('commit to a branch and open a PR')" ([docs/engineering/implement.md](research/1-matt-pocock/skills-repo/docs/engineering/implement.md)). Ticket closing is the human's job. The beta `implement-spec` produces "a PR which implements the entire spec on a single branch", creating "a branch, and a draft PR... marked as 'closing' the spec issue and tickets" ([implement-spec SKILL.md](research/1-matt-pocock/skills-repo/skills/in-progress/implement-spec/SKILL.md)). Merge conflicts: `/resolving-merge-conflicts` "Preserve both intents where possible... Do **not** invent new behaviour. Always resolve; never `--abort`." ([SKILL.md](research/1-matt-pocock/skills-repo/skills/engineering/resolving-merge-conflicts/SKILL.md))

**Contributions from others** (the other direction): `/triage` treats "a PR is an issue with attached code" and moves items through `needs-triage → needs-info | ready-for-agent | ready-for-human | wontfix`, verifying the claim first ("For a bug, reproduce it from the reporter's steps. For a PR, confirm the diff does what it claims"), writing durable agent briefs ("**Don't** reference file paths: they go stale"), and recording rejected enhancements in `.out-of-scope/` ([triage SKILL.md](research/1-matt-pocock/skills-repo/skills/engineering/triage/SKILL.md), [AGENT-BRIEF.md](research/1-matt-pocock/skills-repo/skills/engineering/triage/AGENT-BRIEF.md), [OUT-OF-SCOPE.md](research/1-matt-pocock/skills-repo/skills/engineering/triage/OUT-OF-SCOPE.md)). The repo's own `.out-of-scope/` directory is a live example ([question-limits.md](research/1-matt-pocock/skills-repo/.out-of-scope/question-limits.md) rejects hard caps on grilling questions; [mainstream-issue-trackers-only.md](research/1-matt-pocock/skills-repo/.out-of-scope/mainstream-issue-trackers-only.md)).

**Design questions during a change.** `/prototype`: "A prototype is **throwaway code that answers a question**." Logic questions → "a single shareable HTML file"; UI questions → "several radically different UI variations on a single route". "Throwaway from day one... No tests... Capture it when done": fold the decision into real code, commit the prototype to a `prototype/<name>` branch, leave a context pointer on the issue ([prototype SKILL.md](research/1-matt-pocock/skills-repo/skills/engineering/prototype/SKILL.md)). `to-spec` may inline "a snippet that encodes a decision more precisely than prose can (state machine, reducer, schema, type shape)" from a prototype.

### 4. Tools/harness (Claude Code vs Codex vs Cursor, plan mode, trackers, hooks, subagents, worktrees, `skills` CLI, plugin)

**Harnesses.** Two routes: "**The Claude Code plugin** installs the whole set as a managed, read-only bundle that updates when I ship, so you subscribe rather than fork. **skills.sh** copies editable skill files into your project, so you can hack on them... Pick one: installing both leaves you with every skill twice." ([README.md](research/1-matt-pocock/skills-repo/README.md)) Codex is supported via `agents/openai.yaml` sidecars beside every `SKILL.md` ("`policy.allow_implicit_invocation: false`, the Codex analog of `disable-model-invocation: true`") and `AGENTS.md` symlinked to `CLAUDE.md` ([CHANGELOG 1.2.0](research/1-matt-pocock/skills-repo/CHANGELOG.md)). A native Codex plugin is deferred because Codex's manifest "accepts `skills` only as a **single path string**" and "drops symlinks" on install ([ADR 0002](research/1-matt-pocock/skills-repo/.agents/adr/0002-ship-as-a-claude-code-plugin.md)). skills.sh lists supported agents: "Claude Code, Cursor, Codex, GitHub Copilot, Windsurf, Gemini, Cline, AMP, Antigravity, OpenClaw" ([skills.sh](https://skills.sh/mattpocock/skills)). Matt's own primary harness is Claude Code (everything is verified against it: "Verified 2026-08-05, on Claude Code 2.1.222" — ADR 0002; the aihero articles are titled around Claude Code). Cursor is only mentioned as a skills.sh install target; I found no Matt statement comparing Cursor. Harness-specific rough edges are documented: sub-agent dispatch wording was made harness-neutral in 1.2.3 ("Drop Claude Code's tool and agent-type names... so the step is followable on Codex and other harnesses"), and `/diagnosing-bugs` over-fires on "GPT-5.6-Sol especially" ([docs/engineering/diagnosing-bugs.md](research/1-matt-pocock/skills-repo/docs/engineering/diagnosing-bugs.md)).

**Plan mode.** For grilling: "Leave plan mode off. Plan mode primes the agent to rush toward producing a plan, which is the opposite of staying in inquiry." ([docs/productivity/grill-me.md](research/1-matt-pocock/skills-repo/docs/productivity/grill-me.md)) The "9 things" article notes "/grill-with-docs" has "become a popular replacement for plan mode" ([aihero.dev](https://www.aihero.dev/things-people-get-wrong-with-grill-me-and-grill-with-docs)). The ask-matt docs admit the router has no written answer on plan mode: "whether to use plan mode: that answer is the model's inference, not something written down here" ([docs/engineering/ask-matt.md](research/1-matt-pocock/skills-repo/docs/engineering/ask-matt.md)).

**Issue trackers.** Setup offers GitHub (`gh` CLI), GitLab (`glab`), local markdown (`.scratch/<feature>/`), or "Other (Jira, Linear, etc.): ask the user to describe the workflow in one paragraph; the skill will record it as freeform prose" ([setup SKILL.md](research/1-matt-pocock/skills-repo/skills/engineering/setup-matt-pocock-skills/SKILL.md)). Templates: [issue-tracker-github.md](research/1-matt-pocock/skills-repo/skills/engineering/setup-matt-pocock-skills/issue-tracker-github.md) (including native issue dependencies via `gh api .../dependencies/blocked_by`), [issue-tracker-gitlab.md](research/1-matt-pocock/skills-repo/skills/engineering/setup-matt-pocock-skills/issue-tracker-gitlab.md), [issue-tracker-local.md](research/1-matt-pocock/skills-repo/skills/engineering/setup-matt-pocock-skills/issue-tracker-local.md). "Local markdown is a first-class option, not a fallback: a solo project with no remote is fully supported." ([docs page](research/1-matt-pocock/skills-repo/docs/engineering/setup-matt-pocock-skills.md)) Matt (via Skillselion, X): "Works with literally anything you can connect to programmatically, with zero changes to the skills." ([skillselion](https://skillselion.com/guides/matt-pocock-skills-map)). Niche trackers are formally out of scope ([.out-of-scope/mainstream-issue-trackers-only.md](research/1-matt-pocock/skills-repo/.out-of-scope/mainstream-issue-trackers-only.md)). Known gap: setup "does not run `gh label create`", so labels must be created by hand on a fresh GitHub repo.

**Hooks.** Only in `misc/`: `git-guardrails-claude-code` installs a `PreToolUse` hook on `Bash` that blocks `git push`, `git reset --hard`, `git clean -f`, `git branch -D`, `git checkout .`/`git restore .` ("When blocked, Claude sees a message telling it that it does not have authority to access these commands") ([SKILL.md](research/1-matt-pocock/skills-repo/skills/misc/git-guardrails-claude-code/SKILL.md), [block-dangerous-git.sh](research/1-matt-pocock/skills-repo/skills/misc/git-guardrails-claude-code/scripts/block-dangerous-git.sh)); `setup-pre-commit` installs Husky + lint-staged + Prettier + typecheck + tests as a git pre-commit hook. Neither is promoted or in the plugin.

**Subagents / worktrees.** See axis 1. Worktrees appear only in the beta `implement-spec` and Sandcastle; the promoted skills never create worktrees.

**The `skills` CLI.** `npx skills@latest add mattpocock/skills` (whole set, interactive picker), `npx skills@latest add mattpocock/skills --skill=<name>` (one skill), `npx skills@latest update <name>` ([.agents/install-block.md](research/1-matt-pocock/skills-repo/.agents/install-block.md)). Beta skills are only reachable this way: "The plugin won't give you these. Install one directly: `npx skills@latest add mattpocock/skills --skill=<name>`" ([in-progress/README.md](research/1-matt-pocock/skills-repo/skills/in-progress/README.md)). `scripts/link-skills.sh` symlinks every skill into `~/.claude/skills` and `~/.agents/skills` but is "a dev-only script, intended for use by maintainers of this repo. It is not a supported installer." ([link-skills.sh](research/1-matt-pocock/skills-repo/scripts/link-skills.sh))

**Plugin.** `claude plugins install mattpocock-skills` or in-session `/plugin install mattpocock-skills`; "It's in Claude Code's official marketplace, so there's nothing to add first, and updates arrive automatically." ([README.md](research/1-matt-pocock/skills-repo/README.md)) Accepted into `claude-plugins-official` on 2026-08-05; the listing pins a sha, so "a release reaches installed users when that pin moves, not the moment we tag" ([ADR 0002](research/1-matt-pocock/skills-repo/.agents/adr/0002-ship-as-a-claude-code-plugin.md)). Claude Code docs: "Plugin skills are namespaced by the plugin name" (e.g. `/commit-commands:commit`) and `claude-plugins-official` has auto-update on by default ([code.claude.com/docs/en/discover-plugins](https://code.claude.com/docs/en/discover-plugins)). ### 5. Preferences/opinions (TDD, deep modules, domain modeling, writing-for-agents, grilling, prototypes, what he's against)

- **Grill before you build, every time.** "These are my most popular skills. They help you align with the agent before you get started, and think deeply about the change you're making. Use them _every_ time you want to make a change." ([README.md](research/1-matt-pocock/skills-repo/README.md)) "A rich grilling session is only useful if the decisions reach the build." ([My 'Grill Me' Skill Went Viral, 2026-03-23](https://www.aihero.dev/my-grill-me-skill-has-gone-viral)) On not capping questions: "Grilling is intentionally open-ended... some plans need three questions, some need fifty." ([.out-of-scope/question-limits.md](research/1-matt-pocock/skills-repo/.out-of-scope/question-limits.md)) Use the smartest model for grilling: "A dumb model won't give you good ideas." ([9 things](https://www.aihero.dev/things-people-get-wrong-with-grill-me-and-grill-with-docs))
- **TDD, red→green only, at pre-agreed seams; mocks only at system boundaries; expected values from an independent source of truth.** (axis 3 above)
- **Deep modules — Ousterhout, but with a twist.** "Design **deep modules**: a lot of behaviour behind a small interface, placed at a clean seam, testable through that interface." Rejected framing: "**Depth as ratio of implementation-lines to interface-lines** (Ousterhout): rewards padding the implementation. We use depth-as-leverage instead." Principles: "The deletion test", "The interface is the test surface", "One adapter means a hypothetical seam. Two adapters means a real one." ([codebase-design SKILL.md](research/1-matt-pocock/skills-repo/skills/engineering/codebase-design/SKILL.md)) Vocabulary is enforced: "don't substitute 'component,' 'service,' 'API,' or 'boundary.'" On enforcing depth in TypeScript his answer (per the docs page quoting issue #458) was three options: a class/IIFE, a monorepo package, or dependency-cruiser; "He has separately called Effect the best mechanism and dependency-cruiser the second-best." ([docs/engineering/codebase-design.md](research/1-matt-pocock/skills-repo/docs/engineering/codebase-design.md)) The beta `setup-ts-deep-modules` wires dependency-cruiser so "Public vs private is decided by **depth**: a package's root files are entry points; anything in a subfolder is private" ([SKILL.md](research/1-matt-pocock/skills-repo/skills/in-progress/setup-ts-deep-modules/SKILL.md)).
- **Domain modeling (DDD-lite).** Glossary and ADRs only; "Offer ADRs sparingly"; "Be opinionated" about synonyms. Where he thinks it does *not* pay: "DDD gets less useful the closer it gets to the implementation: the payoff is upstream, in naming and concept alignment, not in aggregates and layer ceremony... On a one-day build, skip it." ([docs/engineering/domain-modeling.md](research/1-matt-pocock/skills-repo/docs/engineering/domain-modeling.md))
- **Writing for agents.** Concepts: context pointers ("The pointer's _wording_, not its target, decides when the agent reaches the material"), the two loads (context load vs cognitive load), information hierarchy/progressive disclosure, completion criteria, leading words ("a compact concept already living in the model's pretraining that the agent thinks with"), pruning (single source of truth, cache, relevance, no-ops: "an instruction the model already obeys by default pays load to say nothing"). Negation is a failure mode: "_Don't think of an elephant_... Prompt the **positive**." ([writing-for-agents SKILL.md](research/1-matt-pocock/skills-repo/skills/productivity/writing-for-agents/SKILL.md)) He prefers user-invoked skills for predictability (axis 6).
- **Throwaway prototypes are kept as evidence.** "Throwaway no longer means deleted... the prototype is captured as runnable evidence on a throwaway branch (`prototype/<name>`) out of main" ([CHANGELOG 1.2.0](research/1-matt-pocock/skills-repo/CHANGELOG.md)). Wayfinder is "'prototypemaxxing', not 'planmaxxing'" ([docs/engineering/wayfinder.md](research/1-matt-pocock/skills-repo/docs/engineering/wayfinder.md)).
- **Primary sources over summaries.** Research must use "official docs, source code, specs, first-party APIs, not a secondary write-up"; `/teach` says "Never trust your parametric knowledge"; conflict resolution traces intent to commits/PRs/issues.
- **Concision.** `/wait-what` is three lines because "Concision skills fail by growing — a 400-line skill still leaves the model verbose" ([CHANGELOG 1.2.0](research/1-matt-pocock/skills-repo/CHANGELOG.md)). The repo bans em-dashes in all prose ([CLAUDE.md](research/1-matt-pocock/skills-repo/CLAUDE.md)) because agent-written text over-uses them (my inference from the changeset wording "so the instructions read as plain text"; the rule itself is verbatim).
- **What he's against:** vibe coding; frameworks that "own the process" (GSD, BMAD, Spec-Kit); "specs to code" automation and "code is cheap"; config knobs ("Config is death"); hard caps on questions; file paths and line numbers in tickets/briefs ("they go stale"); horizontal slicing ("Bulk tests verify _imagined_ behavior"); mocking your own modules; tautological tests; `/compact` as a reflex; `/handoff` as a general bridge ("was oversold"); `--abort` on conflicts; barrel files ("Barrel files that re-export a whole subtree are discouraged"); treating `CONTEXT.md` as a spec; and generic review skills that don't know your standards.

### 6. How the skills fit the workflow (user- vs model-invoked, triggers, chaining rules, entry points, who calls whom)

**The one axis.** "**User-invoked** skills are reachable only when you type them (e.g. `/grill-me`); their job is to orchestrate. **Model-invoked** skills can be invoked by you _or_ reached for automatically by the agent when the task fits; they hold the reusable discipline. A user-invoked skill may invoke model-invoked skills, but never another user-invoked one." ([README.md](research/1-matt-pocock/skills-repo/README.md)) Mechanics: user-invoked = `disable-model-invocation: true` in frontmatter plus `policy.allow_implicit_invocation: false` in `agents/openai.yaml`; the `description` is then human-facing. Model-invoked descriptions "keep rich trigger phrasing ('Use when the user wants…, mentions…, asks for…') so auto-invocation fires." The test: "_could the model usefully reach for this autonomously?_" ([.agents/invocation.md](research/1-matt-pocock/skills-repo/.agents/invocation.md))

**Chaining rules (verbatim from invocation.md):** "Dependencies are expressed as an explicit instruction to **call the Skill tool** with the named skill (`Call the Skill tool with "grilling"`), not deep `../other-skill/FILE.md` cross-references." "The Skill tool takes one skill per call. A step that needs two skills is two calls." "This whole convention only holds when the named skill is **model-invoked**... When a step's precondition is a user-invoked skill (e.g. `setup-matt-pocock-skills`), phrase it as an instruction for the human to act on". Why the tool is named: "A skill that names another skill in prose ('run the `/grilling` skill') does not reliably cause it to load. This is the documented rough edge behind `grill-with-docs`'s most-reported problem." ([.changeset/skill-tool-invocation-terminology.md](research/1-matt-pocock/skills-repo/.changeset/skill-tool-invocation-terminology.md))

**Entry points.** Main flow entry: `/grill-with-docs` (or `/grill-me` with no repo). Matt on X (via Skillselion): "/grill-with-docs? No I think that will remain the easy entry point. /wayfinder for intermediate/advanced users." ([skillselion](https://skillselion.com/guides/matt-pocock-skills-map)) The router `/ask-matt` is the "you don't remember every skill, so ask" entry. On-ramps: `/triage`, `/diagnosing-bugs`, `/wayfinder`. Periodic: `/improve-codebase-architecture` ("once every few days").

**Trigger surface for the model-invoked ones** (frontmatter descriptions): `grilling` fires on "any 'grill' trigger phrases"; `tdd` on "build features or fix bugs test-first, mentions 'red-green-refactor', or wants integration tests"; `diagnosing-bugs` on "'diagnose'/'debug this', or reports something broken/throwing/failing/slow"; `code-review` on "review a branch, a PR, work-in-progress changes, or asks to 'review since X'"; `domain-modeling` on "discussing codebase terminology, writing or editing a CONTEXT.md, or recording or editing an ADR"; `codebase-design` when the user "wants to design or improve a module's interface, find deepening opportunities, decide where a seam goes"; `prototype` on "sanity-check whether a state model or logic feels right, or explore what a UI should look like"; `research` on "wants a topic researched, docs or API facts gathered"; `wizard` on "provisioning infrastructure, setting up credentials or CI secrets... Don't invoke this for steps the agent can perform itself"; `writing-for-agents` on "creating or editing skills, or modifying AGENTS.md or CLAUDE.md"; `resolving-merge-conflicts` on "an in-progress git merge/rebase conflict".
