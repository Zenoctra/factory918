## What to design

The data shapes and the runner under `tests/eval/reviewer/`:

1. The fixture set layout: per round the two briefs byte-for-byte, what else a run needs (the diff, the reviewed head sha, the fixed point), and the `labels` file format: one line per labeled hard finding naming round, axis, id and whatever the scorer needs to decide that a report item re-found it. A brief with no labels is in the set.
2. The scorer's matching rule: how a report item is decided to re-find a label (deterministic anchors in the label line, a blinded judge model, or something else), and how an unlabeled hard finding is counted. Weigh determinism and rerunnability against false matches; the result table must be reproducible from the raw reports by rerunning the scorer.
3. The runner's usage and signatures: how one brief runs against one named model N times through provider dispatch, given that the Claude half cannot be a shell call (the session dispatches it) and the Codex half is. Where each run's report, receipt (input, output, cache read and cache write tokens, wall clock, model reported) and score go under `.scratch/eval/reviewer/`. How a dropout is recorded with its receipt. How the per-model table the ticket wants (recall, unlabeled hard findings per brief, mean output tokens, mean input tokens with cache reads separated, mean wall clock, context failures, run count) is produced. How run-to-run noise is estimated for the recommendation ("cheapest model whose recall is within the run-to-run noise of the best").
4. The scenario table for the runner's refusals (this design has state: files it writes, exit codes, more than one actor), per the runner prompt below: situations down the side (unknown model, unknown brief, N < 1, missing reviewed head, output already exists, Codex refusal, no transcript for a Claude run, report without `hard findings:`, truncated report, and whatever else you find), the input shape across the top, each cell saying what is printed, the exit code, and what the caller does next; the contract defining every term; the test list, one assertion per cell.

Keep it small: bash for orchestration and python3 for parsing and scoring are both used in this repository (`tools/*.py`, `tests/*/*.sh`); pick per piece and say why. No new dependencies.
